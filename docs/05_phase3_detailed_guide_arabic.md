## 1. فكرة المرحلة الثالثة والهدف منها ببساطة

في المرحلتين السابقتين:
* **المرحلة الأولى:** بنينا عقل الـ Agent، وتصنيف النوايا الـ 8، ومصفوفة الصلاحيات (RBAC) باستخدام الـ JWT.
* **المرحلة الثانية:** بنينا الـ Cloud Agentic RAG باستخدام Docling و Qdrant Cloud لمسح واسترجاع سياسات الشركة والـ IT Policies.

### ما الهدف من المرحلة الثالثة؟
في المرحلة الأولى، كانت الردود الخاصة بالتذاكر واستعلامات الداتابيز عبارة عن **نصوص تجريبية ثابتة (Mock Data)**. 
في هذه المرحلة، حولنا النظام لنظام مؤسسي حقيقي يعمل مع **قاعدة بيانات سحابية حية (Supabase PostgreSQL)**:
1. **جدول حقيقي للمستخدمين (`users`):** لتخزين المستخدمين وأدوارهم (`customer`, `support_agent`, `senior_agent`, `admin`).
2. **نظام تذاكر كامل (`tickets`):** حفظ التذاكر بحالاتها وأولوياتها وتصنيفاتها.
3. **عزل بيانات العملاء (Customer Data Isolation):** العميل العادي مستحيل يقرأ أو يشوف غير تذاكره هو فقط، بينما موظف الدعم والأدمن يقدروا يشوفوا طابور التذاكر كامل.
4. **سجل تدقيق رقابي غير قابل للتلاعب (`audit_logs`):** تسجيل كل عملية حساسة أو إنشاء تذكرة للمراجعة لاحقاً.
5. **ربط الـ LangGraph بالداتابيز مباشرة:** لما المستخدم يسأل الشات عن تذاكره، الـ Agent بيستعلم من Supabase فوراً ويرجع له بياناته الحقيقية.

## 2. المكاتب الجديدة المستخدمة في هذه المرحلة

### 1. `supabase>=2.31.0`
* **إيه هي؟** الحزمة الرسمية من Supabase للتعامل مع خدمات المنصة في بايثون عبر بروتوكول PostgREST فائق السرعة.
* **ليه استخدمناها؟** 
  * بتوفر اتصالات سريعة وآمنة عبر HTTPS، وده بيحل مشكلة الـ IPv6 وشبكات الـ Pooler التقليدية.
  * بتدعم الفلترة والاستعلامات المعقدة بدون الحاجة لكتابة كود SQL خام داخل الـ Endpoints.
  * بتستخدم مفتاح الـ `service_role` اللي بيمكّن السيرفر من إدارة البيانات بأعلى درجات الأمان.

### 2. `psycopg2-binary>=2.9.10` و `sqlalchemy>=2.0.38`
* **إيه هما؟** المحركات القياسية الأكثر شهرة في عالم بايثون للاتصال بقواعد بيانات PostgreSQL.
* **ليه استخدمناها؟** لدعم الاتصالات المباشرة واستعلامات الـ DDL والـ Migrations والـ Admin Queries.

## 3. هيكل قاعدة البيانات السحابية (Supabase PostgreSQL Schema)

قاعدة البيانات مصممة وفق أعلى معايير الـ Relational Databases (3NF):

```sql
-- 1. جدول المستخدمين (Users Table)
CREATE TABLE IF NOT EXISTS public.users (
    id VARCHAR(50) PRIMARY KEY,
    email VARCHAR(255) UNIQUE NOT NULL,
    full_name VARCHAR(100),
    role VARCHAR(30) NOT NULL CHECK (role IN ('customer', 'support_agent', 'senior_agent', 'admin')),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);

-- 2. جدول تذاكر الدعم الفني (Tickets Table)
CREATE TABLE IF NOT EXISTS public.tickets (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    description TEXT NOT NULL,
    status VARCHAR(30) NOT NULL DEFAULT 'open' CHECK (status IN ('open', 'in_progress', 'resolved', 'closed')),
    priority VARCHAR(20) NOT NULL DEFAULT 'medium' CHECK (priority IN ('low', 'medium', 'high', 'critical')),
    category VARCHAR(50) NOT NULL DEFAULT 'general' CHECK (category IN ('network', 'hardware', 'software', 'security', 'general')),
    created_by VARCHAR(50) NOT NULL REFERENCES public.users(id) ON DELETE CASCADE,
    assigned_to VARCHAR(50) REFERENCES public.users(id) ON DELETE SET NULL,
    resolution_notes TEXT,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);

-- 3. جدول السجلات الرقابية (Audit Logs Table)
CREATE TABLE IF NOT EXISTS public.audit_logs (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id VARCHAR(50) NOT NULL,
    action VARCHAR(100) NOT NULL,
    details JSONB DEFAULT '{}'::jsonb,
    ip_address VARCHAR(45),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);
```

### حماية الـ Row Level Security (RLS):
تم تفعيل حماية الـ RLS على كافة الجداول لضمان أن مفتاح الـ `service_role` هو الوحيد المتحكم في العمليات الحرجة من الباك إند، مع فتح صلاحيات القراءة العامة للاستعلامات المصرح بها.

## 4. طبقة الـ Services: `DatabaseService`

تم بناء الخدمة في [`app/services/database_service.py`](file:///d:/ldc-Langgraph/app/services/database_service.py) وتقدم واجهات برمجية نظيفة:

1. **`get_user_tickets(user_id)`:**
   * بتعمل فلترة على مستوى قاعدة البيانات: `.eq("created_by", user_id)`
   * ده بيضمن إن حتى لو العميل طلب كل التذاكر، الداتابيز بترجع له تذاكره فقط.

2. **`create_ticket(user_id, data)`:**
   * بتستقبل نموذج `TicketCreate` المدقق بـ Pydantic.
   * بتسجل التذكرة بحالة `open` وتاريخ إنشاء تلقائي بنظام UTC.

3. **`update_ticket(ticket_id, data, actor_role)`:**
   * بتسمح لموظف الدعم أو الأدمن بتعديل حالة التذكرة (`in_progress`, `resolved`, `closed`) وتعيينها لوكيل دعم (`assigned_to`).

4. **`log_audit(user_id, action, details)`:**
   * بتسجل العمليات الحساسة (زي طلب ترقية، أو حذف، أو إنشاء تذاكر) في جدول `audit_logs` كـ JSONB.

5. **`execute_admin_query(query, actor_role)`:**
   * استعلامات آمنة مخصصة فقط للأدمن لفحص الجداول وحالة السيرفر.

## 5. ربط الـ LangGraph Agent بقاعدة البيانات الحية

تم تحديث العقد في [`app/agent/nodes/response_nodes.py`](file:///d:/ldc-Langgraph/app/agent/nodes/response_nodes.py):

* **عقدة `handle_my_tickets_search_node`:**
  * بتستقبل `user_id` من حالة الـ Agent State.
  * بتنادي `database_service.get_user_tickets(user_id)`.
  * بترجع للمستخدم بطاقة منسقة فيها رقم كل تذكرة، عنوانها، حالتها، وأولويتها، واسم الموظف المسؤول عنها.

* **عقدة `handle_ticket_create_update_node`:**
  * بتفحص رسالة المستخدم، وبتستنتج تصنيف العطل تلقائياً (`network`, `hardware`, `software`, `security`).
  * لو كان العميل العادي هو اللي بيحاول ينشئ تذكرة بطريقة غير مصرحة، الـ Router Node بيمنعه بـ `403 Forbidden`.
  * ولو موظف الدعم أو الأدمن، بيتم إنشاء التذكرة وإرجاع رقم التذكرة الجديد (مثل `#4`) فوراً.

## 6. مسارات الـ REST API الجديدة (`/api/v1/tickets`)

في [`app/api/v1/endpoints/tickets.py`](file:///d:/ldc-Langgraph/app/api/v1/endpoints/tickets.py):

| Endpoint | Method | الصلاحيات (Roles) | الوصف |
| :--- | :--- | :--- | :--- |
| `/api/v1/tickets` | `POST` | للجميع (Customer, Agent, Admin) | إنشاء تذكرة دعم جديدة |
| `/api/v1/tickets/my` | `GET` | للجميع (مفصول لكل مستخدم) | استعراض تذاكر المستخدم الحالي فقط |
| `/api/v1/tickets` | `GET` | Support Agent, Senior, Admin | استعراض طابور التذاكر العام بالفلترة (403 للعميل) |
| `/api/v1/tickets/{id}` | `PATCH` | Support Agent, Senior, Admin | تعديل حالة التذكرة أو تعيينها (403 للعميل) |
